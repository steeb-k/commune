What the other clients ship

Commune against nine other Matrix clients, feature by feature. The companion to Commune Spec Gaps, which measures the same client against the standard: this one measures it against what people actually have installed. Off-spec features — the ones no version of the Client-Server API requires — carry a plum tag and a plum edge, because most of them are not worth chasing and should be easy to skip past. The column that matters most is Peers: a row where eight other clients ship something and this one doesn't is a stronger argument than any spec section number.

The field

Ten clients, picked to cover the ceiling (Element Web), the deliberately narrow rewrite (Element X), the desktop peers Commune actually sits beside on a Linux machine, two mobile-first apps, and the parent project. Maturity labels are the ones each project claims for itself.

Everyone but us 3 rows

The rows where the field has settled and Commune hasn't. None of these is a judgement call about taste: each is a thing a person moving from any other client expects to find and does not. Ordered by how little room there is to argue. Three rows left this section on 23 August 2026 — pinned messages, presence, and signing up with the password reset that went with it. Their notes are gone rather than struck; what they became is in the table above, in the Commune cell of each. Spaces went from absent to partial on 24 August 2026, and took its second of three slices the same day. It stays here until it is whole: a feature you can read but not organise with is still a gap.

7 of 9 peers, 1 partial · Spaces Spaces

Every client in this table except Commune’s own parent can browse and join a space. Two thirds of this landed on 24 August 2026: a space has its own sidebar section, opening one shows a page rather than an empty timeline, that page lists the rooms inside and lets each be opened or joined, it can be left, and the public directory lists and labels them instead of filtering them out. Commune has drawn level with Element X’s read-only browsing. What is missing is the word organising: nothing writes m.space.child, so no room can be put into a space from Commune, and there is no picker for the restricted-join-rule editor to call. Nesting is walked one page at a time rather than drawn as a tree, which is where Nheko is still ahead. It is also the blocker under two other rows — authoring a restricted join rule and adding a room to a space both need a space picker first.

7 of 9 peers · MSC3381 — off spec Polls

The one off-spec row worth reading twice. Polls have never been standardised — eight years of Matrix and they are still a proposal — and yet every client here except Nheko and Fractal ships them, including the conservative KDE one. A poll sent into a room Commune is in renders as nothing at all. Skipping it is defensible; not knowing it is missing is not.

4 of 9 peers, 2 partial · Threading Threads

The largest job in the table and the one with the least consensus: Element Web, Element Classic, FluffyChat and Nheko have real threads, Element X keeps them behind Labs and calls them incomplete, NeoChat renders a thread's body but names threads a notable exception, SchildiChat Next and Cinny have none. The only high-value row where being late is still normal.

Where Commune is ahead 3 rows

Three rows where at most three peers ship what Commune ships, and enough of the field is confirmed to trust the count. Knocking, the server notices room and OAuth login would qualify too, but too many peers are unverified on those to claim it; in-room search and the full reporting module miss the cut only because the field has caught up.

0 of 9 peers · Server ACLs Editing which servers can take part

m.room.server_acl is in the spec, moderators need it during a raid, and no other client in this table gives you an editor for it. Element will show you the event in its developer tools. This is the fork's most unusual capability — and the reason is not that it is hard, it is that everyone else assumed a bot would do it.

3 of 9 peers, 1 partial · No spec Several accounts at once

Inherited from Fractal, shared outright only with FluffyChat and NeoChat — Nheko manages it from the command line. Element has never done it on any platform, in any generation. The spec has no opinion — this is purely a client decision, and most clients decided against.

1 of 9 peers · MSC2545 — off spec Sticker and emoji packs you own

Six of the nine peers can display a pack somebody else made; only Nheko can also author and manage one, and Element routes stickers through an integration manager instead. The fork's first addition, and still an unusual one. Behind it sit two near misses: message search inside an encrypted room — a server /search for plaintext rooms and a local index for the rest — which puts Commune level with Element Web and ahead of Element X, which has no in-room search at all; and reporting, where the fork wired up all three endpoints the module defines and most clients wired up one.

How to read the off-spec rows

Twelve rows in this table describe things the Client-Server API does not define. They are tagged and edged in plum so they can be skipped, but they are not all the same kind of thing, and the difference decides whether ignoring one is safe.

Proposals everyone implemented anyway. Polls (MSC3381), voice messages (MSC3245) and custom emoji packs (MSC2545) are unstandardised, universally shipped, and arrive in rooms whether or not this client understands them. Ignoring one of these means rendering someone else's message as a blank or a fallback string.

An architecture, not a feature. MatrixRTC group calls (MSC4143) and simplified sliding sync (MSC4186) are where Element is taking the protocol next. Both are large, both are moving, and neither is a thing that appears in a room and breaks. These are the safest to leave alone — and the most expensive to adopt late.

One vendor's idea. Widgets and the integration manager, Jitsi conference calls, and the recent-emoji list are Element inventions of varying age. Two of them are on the way out inside Element itself. Chasing these is how a client ends up maintaining someone else's deprecations.

Method, and what it can't tell you

The Commune column was read out of this tree, not out of a changelog. The Fractal column is Commune minus what the fork added, cross-checked against the matrix.org ecosystem entry for Fractal, which independently lists spaces, threads, calls and image packs as unsupported.

The other eight columns come from each project's own source tree, changelog or release notes wherever a claim could be traced there, and from the matrix.org client directory's per-client feature flags where it could not. Where the two disagreed, the project's own repository won. Any cell that neither source could settle is marked ? — there are 92 of them across 440 cells, and they are honest gaps in this page rather than gaps in those clients.

Two known conflicts are worth naming. The matrix.org directory lists 1:1 calls as unsupported for FluffyChat while FluffyChat's own site advertises them; the app's claim is taken. And NeoChat's README still lists threads and VoIP as its notable exceptions while its source tree carries a thread-body component — hence a partial, not a yes.
