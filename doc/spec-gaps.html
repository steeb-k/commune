What Commune doesn't speak yet

Every module in the v1.19 Client-Server API, checked against the tree. Eleven gaps: seven with no implementation at all, four implemented partly. Effort is measured in UI work, since the Rust SDK already carries most of the protocol. A second pass, further down, grades what the fork has added since it split from Fractal. Reporting content, server ACLs, recently used emoji and link previews were closed on 22 August, server notices on 23 August; calls moved out of Absent the same day, carried audio and video that evening on one network and between two, and left the partial column when the last event of the module — m.call.negotiate — was answered and then watched working: a camera added to a live voice call, and Element for Android accepting it 850 ms later. The note below says which parts of that evening's work are still unwatched. Presence left Absent on 23 August too, and Pinned Events — a module this page had never listed in either direction — was built the same day and joins the implemented column. Signing up followed it, and the password reset that was the other half of that row landed the same day, so the row is closed rather than halved. Spaces moved out of Absent on 24 August 2026 and took two of its three slices the same day: a space is visible, openable and leavable, the directory lists it, and its page now lists the rooms inside it, each of which can be opened or joined. Writing m.space.child — putting a room into a space — is what keeps the module in the partial column. Room Previews closed the same day, on top of the world_readable flag that came with it: the last twenty messages of a room that says anybody may read them are now read, without joining.

The reordering held — signing up and resetting a password, which went to the top of this list that morning, were both built by the end of the day, and spaces is what stands above everything now.

  1. Spaces — one slice of three left The large one worth paying for, and the blocker on two other rows. The SDK carries all of it on the wire — TimelineFocus::Thread, ThreadListService, thread-aware sending and receipts — so what is left is a thread list, a thread view and pointing the composer at it. Interface work, and an L rather than the XL it looks like.

Five corrections, seven things now closed, a departure, and two that are not what they look like

Closed: a pinned message, in a module this page had missed

Pinned Events appeared in neither column of this page until 23 August 2026 — not absent, not implemented, simply uncounted — while m.room.pinned_events was being read the whole time, in the one room where the spec asks for a different interface entirely. That is the census error worth naming: a module can be half-built by accident and go unmeasured because the half that exists belongs to another module's requirements.

The two readers are siblings now and neither is a generalisation of the other. The notices room collapses its pinned events to one banner, because the module says active notices must be shown "through a special UI, and not the normal pinned events interface"; every other room gets the ordinary list, and the notices room is hard-coded out of it. Merging them would put a notice into the ordinary list, which is the one thing the spec forbids here.

Closed: presence, and the switch that turned out to be an off switch

The plan for this said the publishing half would go behind a setting defaulting to off, on the grounds that it is a wasted request on a server with the module disabled. It is not a request. set_presence is a query parameter on /sync, and the spec says omitting it marks the client online — the SDK's sync presence starts at Online and every sync carries it. So this fork, and upstream Fractal before it, has published presence on every sync either has ever made. Defaulting the switch off would have silently taken users offline for everybody watching them.

On the read side the interesting decision is that unknown is not offline. A server running the module says offline out loud; a server without it says nothing, and the two are different facts. They are drawn the same — no badge — because asking a person to tell those apart from a dot is asking them to diagnose a homeserver. The distinction is kept in the model, where it is cheap, for a profile page that might one day say it in words.

Closed: the call module answers every event it defines

m.call.negotiate was the one thing the spec defined and this client did not answer — a call described again after it is established, which is what adding video to a voice call looks like from the other end. Both of its halves are handled now: their offer is applied and answered with another negotiate, and an answer to one of ours is applied. A renegotiation that fails leaves the call alone, because the media that was flowing before it is still flowing and hanging up over a camera that could not be added takes away a working call.

Two ends can offer at the same moment, and WebRTC's perfect negotiation settles it without either asking the other: the callee is the polite party, so it rolls its own offer back and takes theirs. That is the same shape as the glare rule one layer up, and it has never been reached — it takes two people pressing the same button in the same second.

The reason to send a renegotiation at all is a button that adds the camera to a call placed without one, and that button now works against a real client: the offer went out, Element for Android answered it in 850 ms accepting the video section as recvonly, and the camera chain settled into Playing behind it. Nothing in that path writes SDP — the camera goes into the pipeline, webrtcbin notices that what it sends no longer matches what it last described, and the offer comes from its own on-negotiation-needed, armed only once the call is up since it fires for the first negotiation of every call too.

It took three attempts, and both wrong ones are the same trap: an element added to a running pipeline must be told what state to be in, and sync_state_with_parent() reads the parent's state at an instant when it is briefly Paused — because the sink being added is prerolling. The first attempt synced every child and pushed the microphone, the speaker and webrtcbin down with it. The second synced only the camera's own elements, and the source landed in Paused, produced nothing, so the sink never prerolled, so the pipeline never left Paused. Naming the state outright has no window to be wrong in.

The two interface gaps went with it. A call coming in now rings — the desktop's own sound theme, phone-incoming-call, honouring event-sounds and silent on macOS, which has no such theme — and raises a notification carrying Answer and Decline. A call going out makes no sound: the theme has a ringback and it was taken out again the first time anybody placed a call with it, since the window is already open in front of the caller saying Calling…. The push rule .m.rule.call was already firing for the invite and being dropped as an event of unexpected type; it now defers to the calls module, which is the half that can withdraw the notification when the ringing stops. And m.call.invite is no longer filtered out of the timeline, so a call leaves a row saying what became of it — which is also the spec's ask for the one case where this client does not ring: "when clients suppress ringing for an incoming call invite, they SHOULD still display the call invite in the room and annotate that it was ignored".

What that row cannot say: a call from before the client was running has no outcome. Nothing about a call is written to disk, so the row repeats what the invite said and does not guess at whether anybody answered.

What is still unwatched: a renegotiation arriving here, which needs a peer whose interface offers to add video mid-call and Element for Android's does not; the rollback when two renegotiations cross; the badge for what the other end muted, since the peer to hand sends no stream metadata at all; and the answered and missed cases of the timeline row. The ringtone, the notification with its two buttons and the fullscreen window were all exercised and behave — the ringback going the other way was exercised too, and removed. doc/calls.md carries the same list at the top, where it cannot be missed.

Correction: a thread reply already carries the thread

An earlier version of this page said that a reply into a thread is sent as a plain rich reply. That was true once and is not true against the SDK this client is pinned to. Timeline::send_reply asks infer_reply what kind of reply to build, and outside a thread-focused timeline it answers EnforceThread::MaybeThreaded — which forwards a thread relation the replied-to event already has rather than dropping it. Replying to a message that lives in a thread puts the reply in that thread, today, with no code of ours involved.

The correction matters because it changes what kind of gap threading is. Nothing this client sends is malformed and nothing another client sees is broken by it; the whole of the difference is that this end cannot see a thread. Threaded events sit inline in the main timeline looking like ordinary messages, no thread can be listed, and none can be opened. That is an argument for doing threads carefully rather than urgently — and it moves the row out of the "we are getting this wrong" column, where this page had wrongly put it.

The effort estimate moved with it, from XL to L. The protocol half is already carried: a thread-focused timeline, a thread list service with live updates and pagination, a thread summary with its reply count and its own read receipts on every message, and a flag on the live timeline for hiding threaded events once there is somewhere else to read them. Threading is a stable module of the standard, not a proposal, and what is left of it here is interface work.

Correction: peeking is not the cheap one

This page listed peeking a world_readable room first under what to build next, on the grounds that the timeline is "one call away". The call is one call away. The timeline is not.

Every timeline in this client is built from a room object, and a room object is built from an SDK room — which exists only for rooms sync knows about, meaning rooms already joined, invited to, knocked on or left. A room nobody here has joined has no SDK room, so it can have no timeline, no event objects and none of the message rows that render them. Peeking cannot reuse the stack; it needs a second, smaller one: a model over raw events straight off /messages, and a cut-down row to draw them. The SDK offers no peek to shortcut any of that.

Built on 24 August 2026, and the correction held. It came to a model over raw events, a row of its own and a page on the preview dialog — a second, smaller stack, exactly as this said. The one thing the correction did not see coming: most previews fail anyway, because Synapse will not peek a room it does not already have, and that is the protocol rather than the code.

The Absent table had this right at M all along — it is the ranked list above that oversold it, and the companion page's framing of it as a near miss that repeated the mistake. It is still worth building. It is not the thing to reach for on an afternoon, and it belongs next to browsing a space, because both are "look at a room you are not in" and both hang off the same summary the client already fetches and currently throws half of away.

Correction: knocking was always settable

An earlier version of this page said a room could never be set to knock, because JoinRuleValue folds Knock into Invite. The fold is real; the conclusion drawn from it was not. The join rule subpage has always carried an Allow Invite Requests switch, and Only Invited Users plus that switch sends knock. Knocking worked in both directions before any of this.

The gap the fold actually caused was one row down: a room restricted to a space could not be edited at all, so knock_restricted was unreachable — and the switch was left sensitive over it, so it moved and never saved. That is what was fixed, and the row above now says so.

Correction: the spec has no opt-out for link previews

An earlier version of this page said the opt-outs for URL previews "are account data". They are not. The Client-Server API defines the endpoint and nothing else: there is no m.url_preview account data and no room state event for turning previews off. Element's org.matrix.room.preview_urls state event and its im.vector.web.settings account data are its own inventions, and copying them would have meant putting a name we made up into other people's rooms.

So the switch is a GSettings key, per device, sitting next to the one for GIF search. It defaults to on: in an unencrypted room the homeserver already stored the message carrying the link, so asking it about that link tells it almost nothing new. The cost of a local switch is real and worth naming — turn previews off here and they are still on for the same account on another machine.

One thing the switch deliberately cannot reach: an encrypted room. The endpoint's own text asks clients to consider avoiding it there, since the link is usually what the message is about and the server cannot read the message. That check sits above the setting, and it asks the SDK's three-way encryption state rather than the cached flag — the flag starts at false and is only corrected once an async check answers, so an encrypted room would leak through the window before it flips. Unknown counts as encrypted.

Closed: the quick reactions are yours now

The seven buttons in a message's context menu were a constant in the widget. They now come from m.recent_emoji, which is global account data, so the list is the one every other client on the account is already keeping. A fresh account looks exactly like the old build and the first emoji you react with pushes out the last default.

Ordered by use count, not by recency — a grid that reshuffles after every reaction moves the button out from under the pointer of someone who just learned where it was. ruma exposes the two orderings separately for exactly this reason.

What it cannot reach: the full picker is GtkEmojiChooser, whose "Recently Used" section lives in GSettings with no way in from outside, so it stays per-device. The composer's Insert an Emoji is GTK's own, and never says what was picked. And stickers are mxc: URIs, which want a list of their own.

Closed: the server access list is visible, and refuses to empty itself

A room's m.room.server_acl can now be read and edited from Room Details ▸ Server Access, and a change to it reads as a sentence in the timeline instead of an unsupported state event was received.

The thing worth knowing is in the spec and easy to miss: allow defaults to an empty list, and an empty list denies every server. It is not "no restriction", it is "nobody" — and a room in that state cannot be repaired, because no server is left to send the repair. So the page refuses to save one, rather than asking; shutting out only your own server is severe but recoverable, and that one asks. A room with no ACL at all starts the page from allow: ["*"], so blocking a single server is one action rather than two.

Closed: image packs now write the specified names

Until 22 August 2026 packs were written as im.ponies.room_emotes and im.ponies.emote_rooms, so that Element and FluffyChat could see them. That traded conformance for the convenience of clients which have not caught up, and put a non-standard event in other people's rooms. Commune now sends m.room.image_pack and m.image_pack.rooms.

The cost is real and worth naming: a pack made here is invisible to a client that reads only the unstable names. Nothing that already exists breaks — both names are still read, and a pack is written back under the name it arrived on, so only a new pack picks the stable one.

Correction: Synapse now refuses an ACL that shuts it out

An earlier version of this page said that Synapse accepts an m.room.server_acl denying its own name, and that the confirmation dialog in Commune was therefore the only thing standing in the way. On Synapse 1.159.0, run on 22 August 2026, it is not: the server refused it as well.

Which of the two readings was wrong is not settled. The earlier one may have been taken against an older Synapse, or taken badly. What is worth saying is that the dialog is no longer known to be the last line of defence, and that nothing else on this page rests on it — the empty allow list, which is the unrecoverable case, is refused by Commune outright and does not depend on what the server does.

GIF search leaves Matrix entirely

The sticker picker's second tab queries KLIPY over plain HTTPS, so the search term and the device's IP address go to a service outside the protocol. Nothing in the spec covers this; the closest thing is the Third-party Networks module, which is about bridged room directories and doesn't fit. It's disclosed in settings, which is the right handling — just don't mistake it for a Matrix feature.

Closed: the notices room is pinned, and can no longer be forged

Two halves, and the second is the one worth reading. The first: the m.server_notice tag is now what finds the room — not the sender, not the name, not who created it — and it is checked before m.favourite and m.lowpriority, because putting the room above every ordinary one is the whole point. Active notices are the pinned ones, so those raise a banner over the timeline instead of going into the ordinary pinned messages list — which this client does have since 23 August 2026, and which that room is kept out of.

The second: "Events with a m.server_notice msgtype outside of the server notice room must be ignored by clients." Anybody can send one into any room they can talk in, and the old build drew it with a warning icon and the presentation the real thing gets. So the filter is in the timeline rather than the renderer, and such an event never becomes an item at all.

One thing the tag cannot reach: an invite to the notices room. Room account data is not sent for a room you have only been invited to, so until the invite is accepted the room looks like any other. That is the mechanism, not the client.

And one thing the harness cannot do. @notices:localhost is not a registered user — Synapse speaks as it without ever giving it an account — while the recipient of a notice sits at power level −10 in a room that wants 50 to pin. So nothing outside the server can pin a notice, and the only way to see the banner is to put the server over its own limit and let Synapse pin one itself.

Six of these cannot be checked on a real account

A report goes to the administrator of your own homeserver, which means testing one against a server other people use sends a real complaint to a real person. The restricted rule only appears on a room already restricted to a space, which takes an account that can build one. A server access list, got wrong, shuts people out of a room for good. And link previews need url_preview_enabled, which Synapse ships switched off and most servers leave that way — turning it on somewhere real is a security decision about that server, not a testing convenience, because the endpoint makes the homeserver fetch URLs on a user's say-so. And a server notice comes from the homeserver itself: an active one means that server has actually crossed a limit, which is not a state to wish on a server people are using. And a call needs a TURN server the homeserver will hand out credentials for, which most homeservers do not run and none of them let a visitor reconfigure — the calls above were finally proven against a homeserver of the author's own, pointed at a hosted relay.

So testing/local-homeserver.sh stands up a throwaway Synapse in podman, seeds a space, one room of every rule, a room carrying two successive ACLs, a room of links covering what does and does not earn a card, and an encrypted room where one never can. It reads the reports back out of the server's own tables; its check drives the preview endpoint and says whether the image really arrived as an mxc: URI; and its limit on puts the server over its monthly active user limit so that Synapse writes and pins a server notice of its own; and it runs a coturn beside the Synapse, on host networking rather than published ports — behind a port mapping a TURN server binds one address and advertises another, so the relay is unreachable while every call between two clients on one machine still connects over host candidates and nothing ever says the relay was never usable. None of these are features to try on strangers.

Polls aren't in the spec

Worth stating because their absence looks like a gap and isn't. m.poll.start is still MSC3381 and does not appear in v1.19, so Commune not implementing polls is conformant. It is, though, a visible difference against Element for anyone comparing the two.
