# What still needs a pair of eyes, after the spine moved

The Track 3 sheet. `doc/track3-convergence.md` rewrote every module under
`src/session/`, `src/session_list/` and `src/secret.rs` as a view over
`commune-core` between 1 and 2 September 2026 — thirteen modules and an
audit of the strings — and each record ends with a paragraph of what only a
person at the desktop can judge. **This file is those paragraphs as checks,
in the order to run them.** The compiler, clippy, the core's 123 tests and
the byte-identical bindings passed on every commit; none of them can say
whether a property that used to be computed here and is now mirrored from
the core still reaches the widget that binds it, and that is what every
line below asks.

Same conventions as `doc/eyeball-tests.md`: `[ ]` not yet looked at, `[x]`
looked at and behaves, `[!]` looked at and wrong, with what happened. A
subsection that takes something away opens with a line in italics beginning
**Destructive** and sits at the end of its section; the run sheet reads that
line and marks every check under it. **A result is not recorded until it is
struck here** — the page keeps its marks in one browser and nowhere else.

The first defect this sheet found is already in: a restored session hung at
launch, fixed in `840f76be`. Nothing built before that commit is worth
running this against.

---

## How to run this

Build the `fractal-kotlin` branch on the Linux desktop as before; the binary
must be newer than `840f76be`. `doc/eyeball-track3-run.html` is this file
with checkboxes, generated by `doc/eyeball-page.py track3` and published at
the URL in that page's top comment. Regenerate and republish it whenever
this file changes.

The homeserver harness is the desktop ledger's:

```sh
testing/local-homeserver.sh up      # or `reset` for a clean slate
testing/local-homeserver.sh verify
```

Log in as **alice** — _Another Homeserver_ → `localhost:8008`. The passwords
are `alice-is-testing`, `bob-is-testing`, `carol-is-testing`,
`admin-is-testing`. **Bob** is the second member of nearly everything and
the other end of every two-party check; **carol** has joined nothing. A
second client for bob — a second Commune profile, or Element in a browser —
is needed from the sidebar section on, and the calls section needs it on a
second machine or device with a camera.

**The order is dependency order, not newest first.** Everything needs a
session, so the session list goes first; the sidebar is what every room
check is looked at through; the rest follow what they need. The strings
audit's items sit inside the sections they belong to. Calls are last and
need the harness in `doc/calls.md`.

**The half worth caring about** is the same half as always: the checks
phrased as something that should _not_ happen, and the checks of a value
that changes while a page is open — a name, a count, a state — because a
mirror that is wired once and never updated looks right until then.

## Sessions — modules 1 and 13

The session list is a list model over the core's entries now, and the
session itself mirrors its state, connectivity and profile from the core.
This is where the first defect was.

* [ ] **A restored session comes up.** Close Commune with alice logged in
      and start it again: the room list appears without the "loading
      accounts" spinner staying, and the account switcher shows alice with
      her avatar. This is the check that hung on 2 September, before
      `840f76be`.
* [ ] **Two sessions restore in settings order.** Log in as bob in a second
      account, restart: both accounts are in the switcher in the order they
      were added, and the one that was showing at close is showing again.
* [ ] **A session whose data directory is gone is not restored.** With
      Commune closed, move one session's directory out of the persistent
      data path (its name is the session ID) and start: that account is
      simply absent, no error, and the other is fine. Put it back afterwards.
* [ ] **A session that cannot be restored says so.** Break one session's
      store instead — corrupt its `matrix-sdk-state` database — and start:
      the other account works and a toast names the one that failed, with
      the error's sentence and not a debug dump.
* [ ] **A failed session's row is a row.** The account switcher lists the
      failed session with its user ID and an initial for an avatar, and
      nothing crashes on selecting it.
* [ ] **A login lands on the new session.** From a session already open,
      add a third account: the setup view runs, and at its end the window
      shows the new account, selected in the switcher, with its rooms
      loading — not the account that was showing before.
* [ ] **The offline banner follows the core.** Pull the network cable, or
      stop the harness: the banner appears within a few seconds and names
      the homeserver as unreachable; restore it and the banner goes. Both
      values are mirrored from the core now.
* [ ] **The profile follows the core.** Change alice's display name from
      bob's client: the name in the switcher and the sidebar header updates
      without a restart.
* [ ] **A secret-store failure shows the dialog.** Make the keyring refuse —
      lock it, or run with the secret service stopped — and start: the
      "could not restore previous sessions" dialog appears with the
      keyring's sentence, translated if the desktop is not in English.

### Destructive

_Destructive: these remove accounts; do them last in this section._

* [ ] **Logging out removes the row.** Log the third account out from its
      account settings: its row leaves the switcher at once, the window
      shows the next account, and a restart does not bring it back.
* [ ] **A session signed out elsewhere disappears.** From bob's client,
      sign out one of alice's other sessions: within a sync the session is
      gone from the switcher and its rooms with it, with no error dialog.

## The sidebar — modules 1, 2 and 12

Every row is a mirror of the core's room, every section a filter over the
core's category, and the rows and their drop targets are the core's list.

* [ ] **Every section fills.** With the harness up, the sidebar shows
      Favorites, Rooms, Low Priority and Historical with the rooms the
      harness puts in each, a Spaces entry, and an Invited section only
      when there is an invite.
* [ ] **The sections are in the core's order.** Verifications, access
      requests, invited, server notices, spaces, favorites, rooms, low
      priority, historical — top to bottom, with Explore above and Forget
      below, and no section shown empty.
* [ ] **Join by alias.** Join `#public-room:localhost` from the join dialog: the
      room appears in Rooms and opens.
* [ ] **Knock.** Knock on the harness's knock room, by its ID from bob's
      client: the row appears under the knocking state and, once bob
      accepts, moves to Rooms.
* [ ] **A tombstoned room shows its successor.** Upgrade a room from its
      details page, then open the old room: the banner offers the successor
      and following it opens the new room; the old room's row does not
      vanish.
* [ ] **Name, avatar and topic follow changes.** From bob's client, rename a
      room, set its avatar and change its topic: each reaches the row and
      the header without reopening the room.
* [ ] **A room moves between sections.** Drag a room from Rooms to
      Favorites and back, then to Low Priority: it lands where it was
      dropped, once, and the tag order within Favorites follows the order
      it was given.
* [ ] **Only the right sections appear during a drag.** Start dragging a
      room from Rooms: Favorites and Low Priority appear as targets and
      Rooms does not; drag from Historical and Rooms is the target; drag
      a left room and Forget appears at the bottom; drop outside and every
      section is back as it was.
* [ ] **Explore shows for no drag, Forget only for a left room.** Explore is
      there at rest and gone during a drag; Forget is there only while a
      Historical room is being dragged.
* [ ] **Counts and highlights.** Have bob send a message, then a mention:
      the row's count goes bold, then highlighted; open the room and the
      badge clears as it is read, and the sidebar order follows the latest
      activity.
* [ ] **Typing.** Bob types in a room alice has open: the row's typing
      indicator shows and stops within the timeout.
* [ ] **A direct chat's row.** The chat with bob shows bob's avatar and, with
      presence on, his presence dot.
* [ ] **An invite, with its inviter.** Bob invites alice to a new room: the
      Invited section appears with the row naming bob as the inviter;
      accept and the row moves to Rooms.
* [ ] **An invite from an ignored user is filed under Ignored.** Ignore
      carol, have carol invite alice: the invite does not appear under
      Invited and the room's category reads Ignored; unignore and it
      appears.
* [ ] **The server notice banner.** Send a notice with
      `testing/local-homeserver.sh notice`: the notices room shows in its
      own section and the room shows the banner.
* [ ] **The pinned count, guest access, history visibility, encryption
      badge.** Open the details of a room with pinned events, guests
      allowed, shared history and encryption: each row reads what the
      harness set, and toggling guest access from bob's client changes the
      row without reopening.

### Destructive

_Destructive: this leaves and forgets a room._

* [ ] **Forget removes the row.** Leave a room, then drag it from
      Historical onto Forget: the row leaves the sidebar at once, not after
      a restart — this was the module 1 bug where the row never left.

## Rooms and their members — modules 3 and 4

The member list is a list model over the core's members, and the
permissions, join rule and addresses are mirrors.

* [ ] **The member list, in every membership kind.** Open the members of the
      big harness room: joined, invited and banned members are listed under
      their headings with the right counts.
* [ ] **A member's name changes while the list is open.** Bob changes his
      display name: his row updates in place, in the list and in the
      timeline's sender names.
* [ ] **Two members sharing a name are told apart.** Give carol bob's
      display name: both rows show the user ID beside the name; give her
      own back and the IDs go.
* [ ] **The inviter on an invite.** In a room's members, an invited member
      shows who invited them.
* [ ] **The permissions subpage and every control.** Open Permissions as
      alice, the admin: every power-level row is enabled, changing one and
      reopening shows it kept; open it as bob, a plain member, and every
      row is insensitive.
* [ ] **The join rule in all four values.** Set the room public, invite-only,
      restricted to the space, and knock: each is shown by name after a
      reopen, the restricted value names the space, and the knock switch is
      available only where the rule allows it.
* [ ] **The knock switch.** With the invite rule, turn "users can request an
      invite" on and off: the sentence under the rule changes each way, and
      bob's client agrees.
* [ ] **The addresses subpage's seven edits.** Add a local alias, set it
      canonical, add a second, make it the published one, remove an alias,
      set no canonical alias, add a remote alias: each shows after a reopen,
      and the refusals — a taken alias, a malformed one, removing the
      canonical — each get their sentence and change nothing.

## The timeline, threads and search — module 8, and the audit

The timeline's read state and the sidebar's activity order come from the
core now; a thread row's preview is the core's value put into words.

* [ ] **A room scrolled to its start.** Open a long room and scroll to the
      top: the spinner shows while it paginates and the first message
      arrives with no gap.
* [ ] **A permalink into a focused timeline.** Open a permalink to a
      message from a month ago: the timeline opens focused on it, and
      paginates both up and down from there.
* [ ] **The pinned events.** Open the pinned messages of a room with three
      pinned: all three, in order, and unpinning one from bob's client
      removes it while the page is open.
* [ ] **A thread opened, replied to, and read.** Open a thread, reply, and
      leave it open: the reply appears in the thread and the room's read
      receipt reaches bob's client for the reply.
* [ ] **The read badge and the order.** Have bob message two rooms: both
      badges appear and the rooms rise; open each and its badge clears —
      this is the core's read-state watcher, not the timeline's walk.
* [ ] **The threads list pages.** In a room with more threads than one page,
      open the threads list and scroll: the next page loads, once.
* [ ] **A thread row for a removed message.** Redact a thread's root from
      bob's client: its row reads "This message was removed."
* [ ] **A thread row for a message that could not be decrypted.** In an
      encrypted room, a thread rooted at a message this session has no key
      for reads "Could not decrypt this message"; a thread rooted at a
      sticker shows the sticker's body.
* [ ] **Search, plain and encrypted.** Search a word in a plain room and in
      an encrypted one: results in both; then reindex the encrypted room
      from its settings and search again.
* [ ] **A voice message's name, and a file saved from the viewer.** A voice
      message shows its name and duration; open an image in the media
      viewer and save it: the file lands where chosen with its name.
* [ ] **The server notices room shows its notices.** After
      `testing/local-homeserver.sh notice`, open the notices room: the
      notice is there as a message, and a second one arrives while the
      room is open.

The ignored users, sessions, security, image packs, global account data,
presence and notification settings are all mirrors of the core's.

* [ ] **Ignore and unignore.** From carol's member page, ignore her: her
      messages vanish from the timeline and she is listed on the
      ignored-users page; unignore from there and they return.
* [ ] **The sessions page.** The current session is first with its badge;
      rename it and the name shows after a reopen; sign out another
      session through the password dialog and it leaves the list; sign
      this session out from alice's other client and the list is gone
      with the session, within a sync.
* [ ] **The security page.** Enable recovery, note the key, disable it: each
      state is shown after a reopen and bob's client agrees on the
      cross-signing status.
* [ ] **The sticker picker and the emoticon completion.** In a room with a
      room pack and a pack enabled everywhere: the picker shows both packs
      and `:shortcode` completes from both.
* [ ] **The packs settings page.** Create a pack, edit its name and avatar,
      add and remove an image, enable and disable it everywhere, delete it:
      each shows after a reopen; a pack whose room alice has left shows as

* [ ] **The room details' packs subpage.** The room's pack is listed with its

* [ ] **The safety page's switches.** Media previews and invite avatars, off

* [ ] **An invite with avatars off.** With invite avatars off, an invite from

* [ ] **Quick reactions follow reactions.** React with an emoji not in the

## Verification — module 10

* [ ] **From the setup view.** Log in on a second client and verify from
      the setup view: the request reaches the other client, the emoji are
      compared, they match, and both sides finish.
* [ ] **From another device.** Start from the other client: this one shows
      the request, accepts, compares, and finishes.
* [ ] **A mismatch.** Decline the emoji on one side: both sides show the
      mismatch and the verification ends.
* [ ] **Cancelled from either side.** Cancel from this client, then in
      another attempt from the other: both show the cancellation.
* [ ] **Left unanswered.** Start one and wait two minutes: it times out with
      its sentence, not a spinner.
* [ ] **QR both ways.** Show the QR code and scan it from the other client;
      then scan the other client's code from here.
* [ ] **In-room verification of another user.** Verify bob from his member
      page in a shared room; then start another and leave the room mid-way:
      the verification ends cleanly.
* [ ] **The notification for each request, and its withdrawal.** Each kind
      of request notifies; accepting or cancelling withdraws it.

## Calls — module 11, with the harness

Run per `doc/calls.md`, against the local Synapse, with the two-device
procedure. The calls module is the one place the desktop still owns real
work — the pipeline — driven by the core's signalling.

* [ ] **Placed and answered, both ways.** Alice calls bob, bob answers;
      then bob calls alice. Audio both ways each time, and the window's
      state runs dialing, connecting, connected.
* [ ] **Video added midway.** Turn the camera on during an audio call: the
      other side receives video, and off again removes it.
* [ ] **Mute both ways.** Mute the microphone here and the other side hears
      silence; the other side mutes and this side's indicator shows it.
* [ ] **The other party leaves.** Bob leaves the room during a call: the
      call ends here with the sentence for it.
* [ ] **Declined.** Bob declines: this side ends with "declined".
* [ ] **Unanswered for ninety seconds.** Call bob and let it ring: it ends
      as unanswered at ninety seconds, and bob's client shows a missed
      call.
* [ ] **Glare.** Both call each other at once: one call, connected, no
      second window.
* [ ] **A call from another account in this window does not ring.** With
      bob's account also open in this window, have bob call alice: the
      ringtone does not play and the notification does not appear.
